### Code correctness & error handling

- src/app/lists/ready-made/page.tsx:551-578 (saveList, and the parallel saveActorList/saveGenreList/saveDecadeList server actions gated at 666/725/786) — this is the LIVE ready-made save path (the API route in finding 3 has zero call sites). The profiles row (and everything cascading off it, including the entire `awards` table per supabase/migrations/20251115_create_awards_table.sql:3) is deleted BEFORE auth.admin.deleteUser. - src/components/list/PublicListsHomeSection.tsx:11-57 — a third, un-migrated copy of the exact per-list count/top-5/posters N+1 pattern that src/lib/listEnrichment.ts was created to replace (the auditor found the useUserLists and listEnrichment copies but not this one). - src/contexts/ProfileContext.tsx:109-121 — the app-wide profile auto-creation uses the same colliding `user.email?.split("@")[0]` username as the awards route (finding 7) but is far more reachable: every authenticated page load goes through ProfileProvider, so a user whose email local-part is already taken gets a permanent profile-creation error everywhere, not just on ballot save. Reachability caveat: only the GET half of this route is called (src/app/profile/setup/page.tsx:103); POST currently has zero call sites. - src/app/api/movies/search-live/route.ts:16 — beyond the missing auth check the auditor flagged, the user-supplied `query` is interpolated into the ilike pattern without escaping PostgREST/LIKE metacharacters, so a request with `%` or `_` matches the entire movies table rather than the intended substring.

### Auth flows (signup / login / reset / returning)

- src/app/settings/page.tsx:130-137 — the auth guard redirects on `!user` without waiting for the session to hydrate: `useEffect(() => { if (!user) { router.replace('/'); return; } fetchProfile(); }, [user, router, fetchProfile])`. useAuthState (src/hooks/useAuthState.ts) returns user=null while status==='loading', so a signed-in user who hard-loads or refreshes /settings is bounced to the homepage before the session resolves. The file already imports authStatus and uses it correctly in the render guard at :300 (`if (authStatus === 'loading' || !user) return null`) but not in the effect — exactly the bug src/app/onboarding/page.tsx:61-70 documents and avoids ('Wait for authStatus to resolve past "loading" so we don't bounce a legitimate signed-in user'). /settings is also absent from middleware.ts's isProtectedRoute, so there is no server-side guard to compensate.
- Signup never checks username availability, and collisions are silently renamed. src/app/login/page.tsx:97-111 and src/components/auth/SignupModal.tsx:63-85 validate only length/charset before sending `username` in signUp metadata. The DEPLOYED public.handle_new_user (verified via pg_get_functiondef) rewrites a colliding handle to `<base>_<first6-of-uuid>` and returns silently — the user is never told their public /[username] URL is not what they typed. Worse, public.profiles has NO unique index on username in the live DB (pg_indexes shows only profiles_pkey and profiles_stripe_customer_id_key) despite supabase/migrations/20251202093000_recreate_profiles.sql:4 declaring `username TEXT UNIQUE NOT NULL`, so the client-side fallback insert in src/contexts/ProfileContext.tsx:110-115 can create genuine duplicates; src/app/api/users/[username]/route.ts:20-36 then does `.eq('username', ...).single()`, which fails on a duplicate and 404s BOTH users' public profiles. The already-built availability endpoint (/api/profiles GET, used by the orphaned src/app/profile/setup/page.tsx:103) is the obvious fix and is unused by both signup surfaces.
- supabase/migrations/20251201000000_auto_confirm_users.sql:12-14 — `IF NEW.confirmed_at IS NULL THEN NEW.confirmed_at = NOW()` is dead code: information_schema.columns shows auth.users.confirmed_at is `is_generated = ALWAYS`, `GENERATED ALWAYS AS LEAST(email_confirmed_at, phone_confirmed_at)` in the live database, so Postgres recomputes it after the BEFORE trigger and discards the assignment. Only the email_confirmed_at line does anything. Relevant to finding 1/2's mechanism claims, and a latent failure point if a future Supabase auth-schema change makes that assignment an error instead of a no-op.
- src/app/reset-password/page.tsx (the top-level legacy route, distinct from src/app/auth/reset-password) is `redirect('/auth/reset-password')` with no query-string forwarding, so any legacy recovery link still carrying ?code / ?token_hash / ?error loses its token and lands on the reset page as a token-less 'link expired' state instead of a working reset. Contrast src/app/auth/callback/route.ts:28-34, which explicitly re-attaches code/code_verifier/token_hash/token when it forwards recovery traffic.
- Dimension-wide evidence gap the audit never flags: supabase/config.toml is the LOCAL CLI config (site_url = http://127.0.0.1:3002, additional_redirect_urls pointing at 127.0.0.1:3002, SMTP block commented out), yet findings 1, 2 and 7 all cite it as if it described the deployed Supabase project. Nothing in the repo pins the hosted project's confirmation setting, password minimum, or redirect allow-list — which is the single most load-bearing unknown in this dimension, since it is what actually decides whether signUp() returns a session (finding 1) and whether any confirmation email is ever sent (finding 2). The gap deserves its own item: either adopt `supabase config push` so the file is authoritative, or annotate it as dev-only so future audits stop treating it as production truth.

# Detail: findings and verification notes by dimension

## Code correctness & error handling (CC)

The API/lib/hooks/contexts layers are generally careful about error handling and race conditions (useWatchlist, useCreateAward, the Stripe checkout/webhook routes, and the CSV import pipeline all have deliberate, well-commented mutex/rollback logic), but several routes and hooks still swallow Supabase errors into silent empty/success states or skip validation that peers in the same codebase already apply. **Verifier's dimension assessment:** All twelve findings survive verification at the code level — I found no misread lines, no already-handled cases, and every comparator the auditor invoked (useWatchlist.ts, useCreateAward.ts, stripe/checkout.ts, the isUserAdmin admin routes, import-live.ts) checks out exactly as described. That is an unusually clean hit rate for a correctness pass.

Finding 1 genuinely earns high — it is the only finding combining ongoing charges to a departed user with a webhook that self-inflicts permanent 500 retries for every other subscriber. ### CC-2 — useFollowing.toggleFollow has no per-target mutex, unlike sibling optimistic-update hooks

**Severity:** medium · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/hooks/useFollowing.ts`
