The round-1 audit (2026-08-15) found 6 critical / 13 high findings; a same-week hardening pass (`696069e`, `b26f2a0`) fixed the majority of them. This round confirms that fix work held for auth (AUTH-1/2/5 confirmed fixed in live code) and the RLS/self-grant hole, and finds a **new** set of critical issues the first round didn't surface — mostly exposed by going deeper into areas the first pass only sampled.

**Severity mix (confirmed only):** 6 critical, 11 high, 16 medium, 15 low.

Opus verifiers also surfaced **53 further issues** during independent passes, not yet through a second triage round — see the untriaged appendix.

**What's now confirmed FIXED from round 1** (verified against live code this pass, not just commit messages):
- **PAY-1** (self-grant Premium/admin via RLS) — closed by the column-privilege-lockdown migration.

1. **CC-1.** Unauthenticated SSRF-capable screenshot endpoint

### Code correctness & error handling

- src/app/lists/ready-made/page.tsx (~604-640, plus the parallel saveActorList/saveGenreList/saveDecadeList server actions): this is the LIVE ready-made save path (the API route in finding 4 has no callers). It has the same orphan-empty-list hole, and on either failure it just calls redirect('/lists') with no error surfaced at all, so the user sees a normal lists page and silently loses the save.
- src/app/api/import/library/route.ts:241-246: rows with watched === false are counted into `watchlistAdded` and never written anywhere ('For now just count them'). They are also subtracted out of `skipped` (line 465), and src/app/settings/import/page.tsx never renders watchlistAdded (results block ~415-500), so watchlist rows vanish with zero user-visible trace — while the source card advertises watchlist import (page.tsx:95 'Import your watched films, ratings, and watchlist' and :97 'Upload ratings.csv, diary.csv, or watchlist.csv').
- src/app/api/movies/search-live/route.ts:5-27: no auth check at all, unlike its sibling src/app/api/movies/import-live/route.ts:13-18 which requires a session. Any unauthenticated caller can drive unbounded TMDB searches (external API quota/cost) plus an unindexed `ilike '%query%'` scan over movies, with no rate limit — the same abuse shape as the screenshot route but on a live, in-use endpoint.
- src/app/api/awards/route.ts:133: `const category = (bodyCategory || 'best-picture') as AwardCategory` is a bare cast of unvalidated request-body input, then written at 194-204. supabase/migrations/20251115_create_awards_table.sql:4 has a CHECK constraint on category, so an arbitrary string produces a raw 500. Worth verifying against the live DB — if anon lacks the table grant, this is the concrete live trigger for the swallowed awards error in finding 5.

### Performance & efficiency

- src/components/list/ListDetailView.tsx:187-228 — `saveNewOrder` issues 2N sequential UPDATE round trips on every single drag-and-drop reorder: a first `for` loop writes a negative temp ranking one row at a time (lines 190-203), then a second `for` loop writes the final ranking one row at a time (lines 205-218), plus a movie_lists touch. It is called unconditionally from handleDragEnd (line 183) with no debounce, batching, or upsert. A 100-item list = 200 serial awaits per drop; a 300-item list = 600. This is a worse N+1 than anything the auditor reported and it is on a direct user interaction, not a page load. Fix: one `upsert` of the whole reordered array (or a single RPC), and drop the negative-temp-ranking two-pass dance by deferring the unique constraint.
- src/app/films/page.tsx:139-216, src/app/rankings/page.tsx:81-271, and src/utils/sharedMovieUtils.ts:798-893 (useMovieFilters) — ZERO useMemo in any of the three files (`grep -c useMemo` returns 0 for all). On every render, films/page.tsx recomputes `myFilmsCount` (line 139), `filteredMovies` (141), `groupMovies(...)` full group+sort (166), the visible-group slicing loop (195-202), and `uniqueYears`/`uniqueRanks`/`uniqueGenres` (205-216) — six-plus O(n) passes and a full sort over the entire 3000-movie array. rankings/page.tsx does the same at lines 81, 82, 85, 198, 217, 266, 271, and useMovieFilters repeats it at 846-871. This is the real reason toggling the modal is expensive and it is the mechanism that makes finding 5 bite: every parent render produces brand-new `groupedMovies` array identities, so even a React.memo'd MovieCard with stable callbacks would still be handed fresh props. Wrapping MovieCard in memo without memoizing these derivations will produce little measurable win — the two findings must be fixed together, and the auditor's task list omits half of it.
- src/app/films/[slug]/[id]/page.tsx:24-25 — contradictory caching config: `export const dynamic = "force-dynamic"` immediately followed by `export const revalidate = 3600; // Cache for 1 hour`. force-dynamic wins, so the page is never cached and the inline comment is actively misleading. Every visit to every film page re-runs the movies `select('*')`, auth.getUser(), the similar-movies RPC, and the whole 6-10-query community-stats block. Given the film row is essentially static, this single-line config error probably costs more aggregate latency than the query-parallelization fix the auditor proposed for the same file, and neither the finding nor the suggested task mentions it.
- src/app/films/[slug]/[id]/page.tsx:129-133 — `supabaseAdmin.from('movie_lists').select('id').eq('list_type','watchlist')` fetches the id of EVERY user's default watchlist across the whole database, unbounded, on every film-page render, and then splices all of them into a `.in('list_id', watchlistListIds)` filter at line 162. This grows linearly with total user count (one watchlist row per user) and will eventually blow the PostgREST query-string length — exactly the URL-length hazard the codebase already documents and chunks around in sharedMovieUtils.ts:501-504 and api/import/library/route.ts:266-269. Should be a single count with a join/subquery instead.
- src/utils/sharedMovieUtils.ts:500-527 — the 'rescue ranked movies outside the page-0 range' loop awaits each 50-id chunk serially inside a `for` loop instead of collecting the promises and using Promise.all. A heavy user with a few hundred ranked films outside range(0,2999) pays 5-10 serialized client round trips on top of the initial catalog fetch, directly extending the spinner on Home/Films/Rankings. Cited file, uncited defect.
- src/app/[username]/activity/page.tsx:42 and :83 — the activity feed selects `movies(*)`, pulling every movies column including the heavy JSONB fields (videos, images, watch_providers, alternative_titles, tmdb_reviews) for 21 rows per page, when the UI only renders `thumb_url` and `title`. The auditor read this exact file and only flagged the `<img>` on line 159, missing the much larger payload issue two lines above the query it sits under.
- src/components/list/AddMovieModal.tsx:60-98 — two problems in the typeahead. (a) `select("*")` on movies (line 71) for a 10-row search dropdown, again dragging all the JSONB columns down for thumbnail+title rendering. (b) `existingMovieIds` is in the effect's dependency array (line 98) but the call site passes a freshly-built array on every render — `existingMovieIds={listItems.map(item => String(item.movie_id))}` at ListDetailView.tsx:1185 — so the effect tears down and re-arms its 300ms debounce timer on every parent re-render, and additionally `existingMovieIds.join(",")` (line 77) splices every list item id into the query string unbounded.
- middleware.ts:44-53 — `await supabase.auth.getUser()` (a network call to Supabase auth) runs before the `/films/:slug/:id` early return at line 51, so the result is fetched and discarded on every film-detail request; the broad matcher at line 76 also runs it for every API route. Low severity relative to the above, but it is per-request server latency on the app's most crawlable, highest-volume public route.

### Premium & payment

- Account deletion never cancels the Stripe subscription, so a deleted premium account keeps being charged forever — and poisons the webhook. src/app/api/account/delete/route.ts:80-83 deletes the profiles row (and then the auth user at :102) with no Stripe call anywhere in the file: no stripe.subscriptions.cancel, no stripe.customers.del, no read of stripe_customer_id. A period-end sanity check in isPremiumUser, or a nightly reconcile, would close this cheaply.
- Price migration silently freezes entitlement state for existing subscribers. src/app/api/stripe/webhook/route.ts:47-50 defines isPremiumPrice against the single STRIPE_PREMIUM_PRICE_ID env var, and :159-169 hard `break`s out of customer.subscription.created/.updated without writing anything when the price doesn't match. If Stripe is configured to mark unpaid rather than cancel, no .deleted event ever arrives either (that case IS exempt at :159), so those users hold premium indefinitely. The guard should accept a set of accepted price ids (or match on product), not one env var.
- A native premium subscriber whose payment fails is locked out of the Billing Portal entirely. src/app/settings/page.tsx:627 hides the billing button whenever `isNative && !isPremium`, and isPremium at :235-237 excludes past_due/unpaid. src/app/premium/page.tsx:118 renders null for the same combination. So an iOS user who already pays via Stripe and whose card declines has, on that device, no 'Manage subscription' button, no explanation, and no path to update the card — they can only recover from a desktop browser. This is distinct from the auditor's finding 6 (missing past_due copy) and finding 10 (WebView vs system browser): it is a total loss of access to an existing paid subscription's self-service, and it is also the case Apple's 3.1.1 guidance does allow surfacing (managing an existing subscription is not a purchase). The native guard should key off 'would this start a NEW purchase', not off !isPremium.
- The webhook payload's API version — not the SDK's — is the real version risk, and it is unguarded. src/app/api/stripe/webhook/route.ts:99 and :152 read `subscription.items.data[0]?.current_period_end`. At :152 that object is `event.data.object`, serialized by Stripe at the webhook endpoint's / account's API version, which is chosen in the Stripe dashboard and is NOT influenced by anything in src/lib/stripe.ts. current_period_end only moved onto subscription items in the 2025-03-31 API version, so if the live endpoint created in docs/stripe-go-live-setup.md step 4 lands on an older account default, periodEnd is undefined and subscription_current_period_end is written null on every renewal with no error. The correct mitigations are to pin the API version on the webhook endpoint in the Stripe dashboard and/or fall back to the top-level `(subscription as any).current_period_end` — not to pass apiVersion to the Stripe constructor, which is what the auditor recommended.
- checkout.session.completed can no-op completely silently. src/app/api/stripe/webhook/route.ts:69 wraps the entire handler in `if (userId && customerId)` with no else branch, so a session missing client_reference_id or customer (e.g. a Payment Link or a dashboard-created session) returns 200 {received:true} with zero logging — the one path in this file that doesn't log its skip, versus the explicit console.error at :105-108 and :110-112 for the other skip cases. A paid customer who never gets entitlement would leave no trace to debug from.
