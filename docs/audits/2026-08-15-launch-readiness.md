# Reawarding Launch-Readiness Audit

**Date:** 2026-08-15
**Method:** 7 Sonnet auditors, one per dimension, each independently verified by an Opus reviewer against the live code (and in several cases the live database). Findings below are only the ones that survived verification.

## Executive summary

Across 7 dimensions, the Sonnet auditors reported 51 findings; Opus confirmed 50 and rejected 1 as unsupported by real-world impact. Opus verifiers additionally surfaced **48 further issues** during their independent check passes — several of these (self-grantable Premium, ownership-free ballot editing, import silently overwriting ratings) are more severe than anything in the original findings, so they're included in the backlog below alongside the confirmed items.

**Severity mix (confirmed only):** 6 critical, 13 high, 20 medium, 11 low.

**The five most urgent items, in order:**

1. **PAY-1 (critical).** Any logged-in user can grant themselves Premium (and even admin) by writing directly to `profiles` from the browser console — RLS allows self-UPDATE on every column with no column-level restriction. This was verified against the live database, not just the code.
2. **IMP-1 / LOOP-M1 (critical).** Importing a library **silently overwrites existing ratings** in contradiction of what the UI promises, and a ballot-editing permission gap lets a signed-in visitor overwrite their own ballot with someone else's. Both are one-click-away, real-input bugs, not edge cases.
3. **CC-1 / PAY-3 (critical→high, compounding).** The Stripe webhook is the *only* writer of subscription status and silently drops DB write errors with no retry — combined with PAY-1's open RLS hole, entitlement state has no integrity anywhere in the stack.
4. **PERF-1 (critical).** Every core page (Home, Films, Rankings, Nominees, Year, Onboarding — 9 call sites) fetches up to 3,000 movies and 10,000 rankings rows from scratch with no cache, no pagination, and no sharing between pages.
5. **PAY-M5 (missed by auditor, high-severity in practice).** No in-app-purchase path exists for the Capacitor iOS app at all — Premium is unreachable from an actual App Store build, which is a launch blocker if iOS distribution is in scope, plus real App Store review risk from the current fallback messaging.

# Detail: findings, verification notes, and task briefs by dimension

## Code correctness & error handling (CC)

**Auditor summary (Sonnet):** Audited all route handlers under src/app/api, the shared lib modules, and the hooks/contexts touching Supabase or optimistic client state. The most severe issues are silent error-swallowing around money-affecting and data-destructive paths (Stripe webhook profile sync, account deletion, guest-to-account award migration), plus a recurring pattern of optimistic UI updates (watchlist, follow) that never check write errors or roll back on failure.

**Verifier assessment (Opus):** Unusually high-quality audit for this dimension: all 8 findings CONFIRMED, zero rejections, zero misreads of line numbers or control flow. The auditor correctly identified the dominant defect pattern in this codebase — Supabase's `{ data, error }` tuple being destructured without `error`, or awaited without destructuring at all, so DB failures degrade into 'empty result' or 'silent success' rather than surfacing. Severity calls are defensible; the Stripe webhook 'critical' is if anything under-argued, since I confirmed that webhook is the sole writer of `profiles.subscription_status` with no reconciliation path, making a swallowed error permanently unrecoverable.

Two weaknesses. First, the auditor consistently framed these failures as 'transient DB error / network blip' — plausible-but-rare triggers — when several have deterministic triggers it missed: the guest-award migration hits hard 400s from /api/awards for out-of-range winners or >10 nominees; the library import chunk upsert fails wholesale on duplicate rows in a diary export; the ready-made save fails deterministically on duplicate movieIds. Verifying the constraints (I confirmed the `movie_list_items(list_id, movie_id)` unique index and the awards 10-nominee check) turns three 'could theoretically happen' findings into 'happens on realistic input'.

Second, coverage was route-and-hook-local rather than pattern-wide. Having established the pattern, the auditor stopped short of the adjacent files carrying it: the Stripe checkout route's unchecked `stripe_customer_id` write-back (worst missed item — silently orphans a paying customer and breaks the billing portal), and both premium-entitlement readers (useIsPremium.ts / lib/premium.ts) that convert a query error into 'not premium'. I also found two logic bugs outside the error-handling pattern entirely — the silent 10-nominee ballot truncation and the entirely non-functional revision_number plumbing — suggesting the pass was tuned to one signature and did not do much independent reading of business logic.

### CC-1 — Stripe webhook swallows Supabase update errors, causing silent desync between payment status and Supabase, with no Stripe retry

**Severity:** critical · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/app/api/stripe/webhook/route.ts:61`, `src/app/api/stripe/webhook/route.ts:78-86`

In `POST` for `checkout.session.completed`, `customer.subscription.created/updated/deleted`, the result of `supabaseAdmin.from("profiles").update(...)` is never checked for an `error`. The handler always returns `NextResponse.json({ received: true })` (200) regardless of whether the DB write succeeded. If the update fails (RLS, network blip, schema drift, wrong `stripe_customer_id` match), Stripe is told the webhook succeeded and will NOT retry, so the user's `subscription_status`/`subscription_current_period_end` is permanently stale — a paying user can be left un-premium indefinitely (or vice versa, a cancelled user stays premium) with no logging and no alerting.

**Verifier note:** Verified src/app/api/stripe/webhook/route.ts. Line 61 `await supabaseAdmin.from("profiles").update(update).eq("id", userId)` and lines 78-86 `await supabaseAdmin.from("profiles").update({...}).eq("stripe_customer_id", customerId)` both discard the returned `{ error }`. Line 94 unconditionally returns `NextResponse.json({ received: true })` (200) for every code path including the `default` branch. I also confirmed the blast radius the auditor implies: `grep -rn subscription_status src` shows this webhook is the ONLY writer of `profiles.subscription_status` — there is no reconciliation cron, no on-load Stripe fetch. Both entitlement checks (src/lib/premium.ts:19-25 server-side, src/hooks/useIsPremium.ts:24-33 client-side) read only that column. So a swallowed update error is permanently unrecoverable without manual DB intervention. Severity 'critical' is justified.

**Task brief:** In src/app/api/stripe/webhook/route.ts, capture `{ error }` from every `supabaseAdmin.from('profiles').update(...)` call (checkout.session.completed handler around line 61, and the subscription.created/updated/deleted handler around lines 78-86). If `error` is present, `console.error` it with the event id/type and return a 500 response (not `{received:true}`) so Stripe retries the webhook per its standard retry policy. Add a unit/integration test or manual test plan verifying a forced update error causes a non-200 response.

### CC-2 — Guest award data is deleted from localStorage even when the award migration to Supabase fails

**Severity:** high · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `src/hooks/useGuestRankingStore.ts:293-320`

In `migrateToSupabase`, guest awards are migrated one-by-one via `fetch('/api/awards', ...)`; failures are only `console.warn`'d (lines 308-315), never surfaced, and `awardsMigrated` is not used to gate anything. After the loop, `store.clearAllData()` (line 318) is called unconditionally as long as the earlier `rankings` upsert didn't hard-fail — even if every single award POST failed (e.g. transient network error, session race during sign-up), the guest's `awards` are wiped from localStorage on line 318 while `success: true` is returned with `migratedCount` counting only what succeeded. This is a permanent, silent data-loss bug: a guest who built up Best Picture ballots before signing up can lose them entirely on migration if any award POST fails.

**Verifier note:** Verified src/hooks/useGuestRankingStore.ts:292-320. The award loop only `console.warn`s on `!res.ok` (line 311) and on throw (line 314); `awardsMigrated` gates nothing. Line 318 `store.clearAllData()` runs unconditionally after the loop. I confirmed clearAllData (lines 146-156) does `set({ rankings: {}, awards: {}, hasInteracted: false })` plus `clearAllGuestData()` — so awards really are wiped. Line 320 returns `success: true` regardless. Caller src/utils/authMigration.ts:45-47 only reads `result.success && result.migratedCount > 0`, so the partial failure is invisible to the UI. Two amplifiers the auditor did not mention make this more likely, not less: (a) /api/awards POST returns 400 if `winner_id && !nominee_ids.includes(winner_id)` (route.ts:151) and 400 if `nominee_ids.length > 10` (line 147) — deterministic per-award failures, not just transient ones; (b) the POST body sends `source` and `revision_number` (lines 304-305) which the route never reads, so that metadata is silently dropped even on the success path.

**Task brief:** In src/hooks/useGuestRankingStore.ts `migrateToSupabase` (around lines 292-320), track which award years failed to migrate (e.g. push failed years to an array), only call `store.clearAllData()` when there are zero ranking failures AND zero award failures, and otherwise clear only the successfully-migrated rankings/awards (or leave all guest data intact and return `success: false` with the list of failed years) so a retry is possible and no user data is silently lost. Surface the failure count in the returned result so calling UI can prompt the user to retry.

### CC-3 — Account deletion route ignores all delete errors before permanently deleting the auth user

**Severity:** high · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/app/api/account/delete/route.ts:27-49`

Every `supabaseAdmin.from(...).delete(...)` call for `movie_list_items`, `movie_lists`, `movie_reviews`, `rankings`, `expressions`, `activity_events`, `follows`, `user_follows`, `friendships`, and `profiles` (lines 27-49) discards the returned `{ error }` entirely. If any of these deletes fails (RLS misconfig, FK violation, transient DB error), the route proceeds anyway and calls `supabaseAdmin.auth.admin.deleteUser(userId)` (line 51), permanently removing the auth account while leaving orphaned rows tied to a `user_id`/`actor_id` that no longer resolves to any user — directly contradicting the route's own comment that this exists to guarantee 'everything listed under What Gets Deleted' is actually removed. There is no logging, so such partial failures are invisible.

**Verifier note:** Verified src/app/api/account/delete/route.ts:27-49. Ten `await supabaseAdmin.from(...).delete(...)` statements, none destructured, none logged. Only `deleteUser` at line 51 checks its error. The file's own header comment (lines 5-8) says rows are removed explicitly 'so this works regardless of whether a given table's cascade is actually wired up' — which is exactly the assumption that makes a swallowed failure produce unreachable orphans. One partial mitigation worth noting: `awards` is not in the explicit delete list, but supabase/migrations/20251115_create_awards_table.sql line 3 has `references public.profiles(id) on delete cascade`, so the line 49 profiles delete does cascade awards away — unless that profiles delete is itself the one that fails, in which case the user's entire ballot history survives account deletion while the auth user is gone.

**Task brief:** In src/app/api/account/delete/route.ts, capture the `{ error }` from each `supabaseAdmin.from(...).delete(...)` call between lines 27-49, collect any errors, and if any occurred, log them (include table name and userId) and return a 500 with details BEFORE calling `supabaseAdmin.auth.admin.deleteUser(userId)` — do not delete the auth user if upstream data deletion failed, since that guarantees unreachable orphan rows.

### CC-4 — Optimistic watchlist toggle has no error handling or rollback, and races on rapid repeated clicks

**Severity:** medium · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `src/hooks/useWatchlist.ts:45-59`, `src/hooks/useWatchlist.ts:62-67`

`toggle()` optimistically flips `watchlistMovieIds` (lines 49-53) before awaiting the Supabase `delete`/`insert` (lines 54-58), and never checks the returned `{ error }` or reverts state on failure — if the write fails, the UI permanently shows the movie as on/off the watchlist while the DB disagrees, with no error surfaced to the user. Separately, `isOnWatchlist` is read once from the `watchlistMovieIds` closure (line 48) before the state update; if `toggle` is invoked twice in quick succession for the same movie (e.g. double-tap) before React re-renders, both calls compute the same stale `isOnWatchlist` and issue the same operation twice (e.g. two `insert`s, which can throw a duplicate-key error that's silently ignored, or two `delete`s that are silently no-ops), so state and DB can end up inconsistent. `removeIfWatched` (lines 62-67) has the identical unchecked-error pattern.

**Verifier note:** Verified src/hooks/useWatchlist.ts. Line 48 reads `isOnWatchlist` from the `watchlistMovieIds` closure captured by the useCallback (dep array line 59), lines 49-53 flip state optimistically, lines 55/57 await delete/insert with no `{ error }` capture and no rollback. `removeIfWatched` (62-67) is identical. The double-tap race is real: both invocations in the same render frame close over the same `watchlistMovieIds`, so both compute the same `isOnWatchlist` and both issue an insert. I confirmed the duplicate insert actually errors rather than being a harmless no-op — supabase/migrations/20250715000000_create_base_schema.sql:203-204 declares `CREATE UNIQUE INDEX movie_list_items_list_movie_unique ON movie_list_items(list_id, movie_id)`. That unique-violation is silently discarded. Also note line 30-36 in the load effect drops `error` on the initial read the same way.

**Task brief:** In src/hooks/useWatchlist.ts, capture `{ error }` from the `insert`/`delete` calls in `toggle` (lines 55 and 57) and in `removeIfWatched` (line 66); on error, revert the optimistic `setWatchlistMovieIds` update and surface the failure (e.g. via a toast or returned error) to the caller. Additionally guard against double-invocation races, e.g. by tracking an in-flight movieId set/mutex similar to the per-year lock pattern already used in src/hooks/useCreateAward.ts, so a second rapid toggle for the same movie waits for the first to resolve instead of computing from stale state.

### CC-5 — useFollowing toggleFollow has no error handling/rollback, and load() silently swallows query errors

**Severity:** medium · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `src/hooks/useFollowing.ts:97-123`, `src/hooks/useFollowing.ts:43-91`

`toggleFollow` (lines 97-123) optimistically updates `followingIds` (lines 104-109) then awaits `supabase.from("follows").delete(...)` or `.insert(...)` (lines 112-119) without ever reading `{ error }` — a failed follow/unfollow (e.g. RLS denial, duplicate-key on insert) leaves the UI permanently showing the wrong follow state with no user-facing error and no rollback. Separately, the `load()` effect (lines 43-91) destructures `{ data }` from three separate Supabase queries (follows-following, follows-followers, my-following) and never checks the corresponding `error`, so a failed query silently renders as 'this user has zero followers/following' instead of surfacing a load error.

**Verifier note:** Verified src/hooks/useFollowing.ts. toggleFollow lines 97-123: optimistic setFollowingIds at 104-109, delete at 112-115 / insert at 117-119, neither result destructured, no rollback, return type is `Promise<void>` (line 22) so the caller cannot learn of failure either. load() lines 43-91 destructures only `{ data: followingRows }` (47), `{ data: followerRows }` (53), `{ data: myFollowing }` (81) — all three drop `error`, and `?? []` at 68/74/86 converts a failure into a rendered empty state. The hook's exported type UseFollowingResult (13-23) has no `error` field, confirming consumers cannot distinguish the two cases.

**Task brief:** In src/hooks/useFollowing.ts: (1) in `toggleFollow` (lines 97-123), capture `{ error }` from the delete/insert calls and revert the optimistic `setFollowingIds` update plus notify the caller on failure; (2) in the `load()` effect (lines 43-91), check `error` on each of the three queries and set an error state (the hook currently exposes no `error` field) so consuming components can distinguish 'no followers' from 'failed to load followers'.

### CC-6 — CSV/library import silently drops failed ranking upserts into the generic "skipped" bucket

**Severity:** medium · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/app/api/import/library/route.ts:210-219`

In the batch upsert loop (lines 210-217), `if (!error) imported += chunk.length;` is the only handling of the upsert result — when a chunk's upsert fails (e.g. transient DB error, malformed row), the error is discarded entirely (not logged, not collected), and those rows are not counted toward `imported`. `skipped` is then computed as `rows.length - imported - notFound.length - watchlistAdded` (line 219), so a genuine server-side write failure is indistinguishable in the response from rows that were legitimately unmatched/skipped for content reasons. Users importing a large Letterboxd/IMDb library get a wrong 'X skipped' count with no indication some of their watched films failed to save due to a server error, and have no way to know which rows to retry.

**Verifier note:** Verified src/app/api/import/library/route.ts:210-217 — `const { error } = await supabase.from("rankings").upsert(chunk, ...)` followed only by `if (!error) imported += chunk.length;`, with no log and no failed-row tracking; line 219 folds the difference into `skipped`. ImportResult (26-33) has no field to express a save failure. The auditor understated this: because `rankingsToUpsert` is built row-by-row from `rows` (182-198) with no dedup on `movie_id`, any Letterboxd/IMDb export containing the same film twice (a common case in diary/rewatch exports, or two rows whose distinct imdbIds resolve to the same local movie) produces duplicate conflict keys in one payload, which makes Postgres reject the whole statement with 'ON CONFLICT DO UPDATE command cannot affect row a second time'. That silently discards up to CHUNK=500 rows at once, not a stray row.

**Task brief:** In src/app/api/import/library/route.ts, in the chunked upsert loop (around lines 210-217), log `error` (with chunk index/size) when the upsert fails, and track failed rows separately (e.g. a `failedToSave: string[]` array of title/year) rather than folding them into the generic `skipped` count. Surface this new field in the `ImportResult` type (lines 26-33) so the client can tell the user which titles need to be retried instead of assuming they were simply unmatched.

### CC-7 — Public user profile API swallows movies/awards query errors and returns a fake empty-profile 200 response

**Severity:** medium · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/app/api/users/[username]/route.ts:40-70`

A transient DB error on either query therefore renders as 'this user has rated/seen 0 films and has 0 awards' on their public profile instead of a load error, which is indistinguishable from a genuinely new user and is misleading for both the visited user and any visitor.

**Verifier note:** Verified src/app/api/users/[username]/route.ts. Line 52 `const allMovies = movies || []` runs BEFORE the error check, and lines 53-55 only `console.error` moviesError; lines 68-70 do the same for awardsError, then line 73 `(awards || [])`. **Task brief:** In src/app/api/users/[username]/route.ts, when `moviesError` (line 53) or `awardsError` (line 68) is set, return a 500 (or otherwise pass an explicit error/degraded flag in the JSON body) instead of silently continuing with empty arrays, so src/hooks/usePublicProfile.ts can distinguish 'no data' from 'failed to load' and show an appropriate error state rather than an empty profile.

### IMP-4 — No progress feedback for large imports, and all writes are gated behind slow external calls that can time out with zero rows saved

**Severity:** medium · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `src/app/api/import/library/route.ts:35-38,134-217`, `src/app/settings/import/page.tsx:377-391`

**Task brief:** Reorder src/app/api/import/library/route.ts so already-locally-matched rows are upserted immediately after the local-match step (around line 130), before the live TMDB backfill loop runs, so a timeout during backfill doesn't discard writes that had already succeeded. ### Additional issues found by the Opus verifier (IMP-M*)

**IMP-M1.** Duplicate movie_id rows inside a single upsert chunk will abort the entire chunk. src/app/api/import/library/route.ts:182-217 builds one rankingsToUpsert entry per CSV row with no dedup by movie_id, then sends chunks of 500 with ON CONFLICT DO UPDATE. Postgres raises 'ON CONFLICT DO UPDATE command cannot affect row a second time' (SQLSTATE 21000) when the same conflict key appears twice in one statement. The upload UI explicitly invites diary.csv (page.tsx:267 'ratings.csv, diary.csv, or watchlist.csv'), and Letterboxd diary.csv has one row per viewing — any rewatch produces duplicate (title, year) rows that resolve to the same movie_id. Combined with the swallowed error at route.ts:216, the result is 500 rows silently lost per affected chunk and a green 'Import complete' screen. This is the most likely concrete failure in the whole flow and no finding covers it.

**IMP-M2.** Non-premium users hit the paywall only after the full funnel, and get a dead end with no upgrade path. src/app/api/import/library/route.ts:61-66 returns 403 only after source selection, file upload, parse, preview, and clicking Import; src/app/settings/import/page.tsx:179-181 dumps the message into `parseError`, rendered as a plain red error box (lines 362-367) with no link to /premium (the import page contains zero references to 'premium' or the upgrade route). Finding 2 mentions the gate but frames it as an onboarding problem; the in-page dead end is a separate, concrete UX defect.

**IMP-M3.** The import source is captured and then thrown away. src/app/api/import/library/route.ts:69 destructures `source` from the body but never uses it again (grep confirms line 69 is its only occurrence), while `imported_from` (line 196) is set to `importedAt`, an ISO timestamp — so the rankings.imported_from column, whose name and `string | null` type (src/types/supabase.ts:1116) clearly imply provenance, stores a timestamp instead of 'letterboxd'/'imdb'. There is consequently no way to attribute a rating to its source, no way to undo an import, and no way to distinguish imported ratings from hand-entered ones.

**IMP-M4.** The 'Films imported' headline number counts writes attempted, not films newly added. route.ts:216 adds `chunk.length` regardless of how many rows were inserts versus updates of pre-existing rankings, so a user re-running the same file sees the full count again under the label 'Films imported' (src/app/settings/import/page.tsx:411-412). **IMP-M5.** The CSV parser cannot handle quoted fields containing newlines. src/app/settings/import/page.tsx:36-46 does `text.trim().split(/\r?\n/)` and only then applies the quote-aware parseCSVLine per line, so a single embedded newline (Letterboxd Tags, and any reviews/notes column) desynchronises the field mapping for that row and every column offset after it — producing garbage titles/years that then surface as 'not in our catalog' with no error shown.

**IMP-M6.** No server-side validation of the posted rows. route.ts:68-73 only checks that `rows` is a non-empty array; there is no bound on rows.length, no type-checking of individual rows, and no clamping of `rating` to 1–10. I verified in the live DB that rankings has no CHECK constraint on `ranking` (only rankings_pkey, rankings_user_movie_unique, and the movie_id FK), so a crafted POST can write arbitrary integers into ranking — which then feed the 7+ nominee-emergence rule — or submit an unbounded row count to tie up the function.

**IMP-M7.** IMDb exports are not filtered by title type. src/app/settings/import/page.tsx:64-81 (normalizeIMDb) reads only Title / Year / Const / Your Rating and ignores IMDb's 'Title Type' column, so TV series, episodes, video games and shorts are all forwarded as films. Rows carrying a tt-id will mostly fail cleanly, but any row missing one goes to `searchTmdbMovies(row.title)` (route.ts:147) against TMDB's *movie* endpoint, where a same-titled unrelated film released in the same year would be accepted and rated on the user's behalf.

**IMP-M8.** The live-backfill cap is far more punishing than the code comment implies, given catalog size. The movies table holds 4,355 rows (verified), so for a typical 1,000+ film Letterboxd export the large majority of rows miss the local catalog and queue for backfill, of which only LIVE_BACKFILL_CAP=75 are attempted per request. The done-screen copy 'r+e-import the file to pick up more of them' (src/app/settings/import/page.tsx:439-442) therefore means roughly a dozen manual re-uploads — and each re-upload re-upserts every already-matched row, re-triggering the finding-1 overwrite each time.

## Premium & payment (PAY)

**Auditor summary (Sonnet):** The Stripe subscription flow is wired end-to-end for the common happy path (checkout, webhook sync, portal, two real server-side entitlement gates in the import/ready-made-list routes), but it has one critical security hole and several launch-blocking gaps: profiles RLS lets any authenticated client write their own subscription_status directly (full premium bypass with zero payment), a client-side-only "premium" stats panel leaks its gated data to free users regardless, past-due subscribers get funneled back through Checkout instead of the Billing Portal (risking duplicate subscriptions), webhook DB-write failures are silently swallowed with no retry or logging, there is no iOS in-app-purchase path at all (App Store guideline risk plus zero iOS revenue), and refund/payment-failure handling is effectively absent.

**Verifier assessment (Opus):** Strong audit overall — all six findings survive scrutiny, and the top one is not merely plausible but decisively provable: I confirmed it against the live database (pg_policies shows UPDATE on public.profiles gated only by `auth.uid() = id`, and information_schema.column_privileges shows `authenticated` and `anon` holding UPDATE on all 20 columns, including subscription_status, stripe_customer_id and is_admin). Self-granting Premium from the browser console is real, and the entitlement chain (src/lib/premium.ts, src/hooks/useIsPremium.ts) reads nothing else, so every server gate collapses with it. No finding was rejected; the file:line citations were accurate throughout, which is unusual.

Two places where the audit was imprecise rather than wrong. (a) The SELECT-leak note in finding 1 says billing metadata is exposed to "any authenticated reader" — it is actually worse: an `Anonymous users can view profiles` policy with `USING (true)` plus an anon SELECT grant means logged-out callers can enumerate stripe_customer_id. (b) The finding-1 remediation would break the app if applied literally: src/app/api/stripe/checkout/route.ts:33-36 writes stripe_customer_id through the RLS-scoped session client, so revoking client UPDATE on billing columns without first moving that write to supabaseAdmin takes down new-customer checkout. Finding 5's factual half (no IAP integration, all three native entry points disabled) is solid; its App Store 3.1.1/3.1.3 rejection prediction is a policy judgement, not something verifiable from the code, and should be labelled as such.

The main gaps are in webhook robustness and root-cause scope. The audit treated the RLS hole as a billing problem when it is a general column-write problem — is_admin is self-grantable through the identical mechanism, a strictly larger blast radius that the proposed fix would leave open. On the webhook, the audit caught the swallowed error but missed three adjacent failure modes that the suggested fix does not address: a zero-row `.eq()` match is not an error and stays silent; there is no event-ordering or idempotency protection; and there is no validation that the subscription is even for the premium price. Finally, the highest-frequency money bug in this codebase is probably the one nobody flagged — `/settings?checkout=success` is never read and the profile is fetched once on mount, so a customer who just paid routinely lands on "Free plan / Unlock Premium — $19/yr" while the webhook is still in flight, one click away from a second subscription. ### PAY-1 — Users can self-grant Premium by writing directly to profiles.subscription_status (RLS has no column-level protection)

**Severity:** critical · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `supabase/migrations/20251202101500_align_profiles_schema.sql:23-24`, `supabase/migrations/20260722000000_add_subscription_fields_to_profiles.sql`, `src/lib/supabaseBrowser.ts`, `src/hooks/useIsPremium.ts`, `src/lib/premium.ts`

The `profiles` table RLS policy is `CREATE POLICY "Enable update for users based on id" ON public.profiles FOR UPDATE USING (auth.uid() = id);` — no `WITH CHECK`, no column-level GRANT/REVOKE, and no trigger guarding `subscription_status`/`stripe_customer_id`/`subscription_current_period_end`. Because Postgres RLS falls back to the `USING` clause as the `WITH CHECK` clause when none is given, any authenticated user updating their own row can set ANY column, including the billing ones. The browser client (`src/lib/supabaseBrowser.ts`) uses the anon key and is fully subject to this RLS, so a user can simply run `supabase.from('profiles').update({ subscription_status: 'active' }).eq('id', user.id)` from the browser console (or a raw PostgREST PATCH with their own JWT) and instantly pass both `isPremiumUser()` (src/lib/premium.ts) and `useIsPremium()` (src/hooks/useIsPremium.ts), which only check `profiles.subscription_status` — with zero payment. This also means every server-side gate that trusts `isPremiumUser` (ready-made list save, CSV import) is bypassable the same way. Separately, the SELECT policy (`USING (true)`) exposes every user's `stripe_customer_id` and `subscription_status` to any authenticated reader, which is unnecessary billing-metadata leakage.

**Verifier note:** Verified in code AND against the live database. supabase/migrations/20251202101500_align_profiles_schema.sql:23-24 creates `FOR UPDATE USING (auth.uid() = id)` with no WITH CHECK; no later migration adds column-level protection (grepped REVOKE/GRANT across supabase/migrations — only rankings-related grants exist). Live DB confirms it: pg_policies shows two permissive UPDATE policies on profiles (`USING (auth.uid()=id)`, with_check null / `(auth.uid()=id)`), and information_schema.column_privileges shows `authenticated` (and `anon`) hold UPDATE on all 20 profiles columns including subscription_status, stripe_customer_id and is_admin. src/lib/premium.ts:19-25 and src/hooks/useIsPremium.ts:24-32 read only profiles.subscription_status, and both server gates (src/app/api/lists/ready-made/save/route.ts:19, src/app/api/import/library/route.ts:61) go through isPremiumUser. The SELECT-leak sub-claim is understated, not wrong: the policy set includes `Anonymous users can view profiles` USING(true) and anon holds SELECT on all 20 columns, so stripe_customer_id is exposed to logged-out callers, not just authenticated ones.

**Task brief:** In supabase/migrations, add a new migration that removes billing-column write access from the client role. Preferred approach: move stripe_customer_id / subscription_status / subscription_current_period_end out of the client-writable `profiles` UPDATE policy — either (a) split them into a separate `billing_profiles` table with RLS `USING (false)` for INSERT/UPDATE/DELETE (service_role only, matching how src/app/api/stripe/webhook/route.ts already uses supabaseAdmin), and update src/lib/premium.ts, src/hooks/useIsPremium.ts, and src/app/settings/page.tsx to read from it via a join or separate query; or (b) keep the columns on `profiles` but add `REVOKE UPDATE (stripe_customer_id, subscription_status, subscription_current_period_end) ON public.profiles FROM authenticated;` plus a `WITH CHECK` that re-asserts the pre-existing values for those columns unless the caller is service_role. Also tighten the SELECT policy so `stripe_customer_id`/`subscription_status` aren't returned to arbitrary authenticated readers (e.g. a security-definer view exposing only public profile fields). Acceptance criteria: after the fix, `supabase.from('profiles').update({subscription_status:'active'}).eq('id', <own-id>)` from an anon-key client fails or silently no-ops on those columns, while /api/stripe/webhook/route.ts (using supabaseAdmin) continues to update them successfully; existing premium users' status is unaffected by the migration.

### PAY-6 — No handling of refund events or payment-failure UX — refunded customers can keep access indefinitely, and past-due customers get no in-app warning

**Severity:** low · **Effort:** medium · **Verdict:** CONFIRMED

**Files:** `src/app/api/stripe/webhook/route.ts:28-92`, `src/app/settings/page.tsx:599-639`

The webhook switch only handles `checkout.session.completed` and `customer.subscription.{created,updated,deleted}`. There is no handler for `charge.refunded` / `charge.dispute.created`. If support issues a refund via the Stripe Dashboard without also canceling the underlying subscription, `profiles.subscription_status` never changes and the user keeps premium access indefinitely with no automatic reconciliation. Separately, when a renewal payment fails and status flips to `past_due`, nothing in the UI (src/app/settings/page.tsx Premium card) tells the user their payment is failing or gives them a way to fix it in-app — instead, once `past_due`, the Premium card just reverts to showing "Free plan" (see the related Checkout/Portal-routing finding), so there's no dunning messaging at all, only whatever Stripe's own email retry settings send.

**Verifier note:** src/app/api/stripe/webhook/route.ts:28-92 switches on exactly four event types; grep for 'charge.'/'invoice.'/'refund' across src/app/api/stripe/ returns nothing, so charge.refunded, charge.dispute.created and invoice.payment_failed are all unhandled (they fall through to `default: break`). A dashboard refund does not mutate the Stripe Subscription object, so no handled event fires and subscription_status stays 'active' — the described stale-entitlement outcome holds. The dunning half is also confirmed: src/app/settings/page.tsx:599-639 renders only a binary isPremium ? 'You're on Premium' : 'Free plan' card with no past_due branch, and no other component references 'past_due' (grep of subscription_status consumers: settings/page.tsx, useIsPremium.ts, premium.ts — all treat non-entitled statuses identically). 'low' is a fair severity given manual-refund frequency.

**Task brief:** In src/app/api/stripe/webhook/route.ts, add a case for `charge.refunded` (and optionally `charge.dispute.created`) that looks up the associated subscription/customer and, if the refund is for the full subscription amount, cancels the Stripe subscription (`stripe.subscriptions.cancel`) so the existing `customer.subscription.deleted` handler naturally revokes entitlement — or at minimum logs a flag for manual follow-up. Separately, add a lightweight in-app banner in src/app/settings/page.tsx (and optionally the homepage) when `subscription_status === 'past_due'` explaining the payment failed and linking straight to the Billing Portal. Acceptance criteria: a full refund on a subscription's latest invoice results in `profiles.subscription_status` being updated to a non-entitled value within one webhook round-trip; a past_due profile sees an explicit in-app message with a working link to the Stripe Billing Portal.

### Additional issues found by the Opus verifier (PAY-M*)

**PAY-M1.** src/app/api/stripe/checkout/route.ts:33-36 — the `stripe_customer_id` write goes through the RLS-scoped session client (createSupabaseServerClient), not supabaseAdmin. This is the app's own dependency on the finding-1 hole: any fix that revokes client UPDATE on billing columns will break checkout unless this write is moved server-side/admin. The auditor's remediation for finding 1 never mentions it, so applying the suggested fix as written would break new-customer checkout. Its error is also unchecked — if it fails, the freshly created Stripe Customer is orphaned and a brand-new customer is created on every retry, fragmenting billing history.

**PAY-M2.** supabase/migrations/20260106000001_add_is_admin_to_profiles.sql + src/lib/adminAuth.ts:43-52 / src/hooks/useIsAdmin.ts:28-32 — `profiles.is_admin` sits behind the exact same unrestricted UPDATE policy and column grant (verified live: `authenticated` holds UPDATE on is_admin). Any logged-in user can `update({is_admin:true})` on their own row and gain the admin dashboard, which is a strictly larger blast radius than self-granting premium. Finding 1's proposed remediation only covers the three billing columns and would leave this open.

**PAY-M3.** src/app/settings/page.tsx:81-134 vs src/app/api/stripe/checkout/route.ts:47 — Stripe redirects to `/settings?checkout=success`, but nothing reads that query param; `fetchProfile` runs once on mount with no poll, retry, or router.refresh. Because the webhook is asynchronous, a user who just paid routinely lands on a page that says 'Free plan' with an 'Unlock Premium — $19/yr' button. Clicking it starts a second Checkout Session — the same duplicate-subscription outcome as finding 2, but reachable by a brand-new happy-path customer, not just a past_due one.

**PAY-M4.** src/app/api/stripe/webhook/route.ts:78-86 — `.update(...).eq("stripe_customer_id", customerId)` matching zero rows is not a PostgREST error, so even after adding the error check the auditor recommends in finding 3, subscription events for a customer whose profile link is missing or stale are still dropped silently. The handler needs an affected-row assertion (e.g. `.select('id')` and check length) plus logging, not just an error check.

**PAY-M5.** src/app/api/stripe/webhook/route.ts:68-88 — no idempotency or ordering protection. Stripe does not guarantee event delivery order and retries duplicate events; the handler blindly last-writes `subscription.status`, with no comparison against `event.created`, no stored processed-event-id table, and no guard against a delayed older event overwriting newer state (e.g. a late `past_due` clobbering a recovered `active`). This is a distinct failure mode from the swallowed-error finding.

**PAY-M6.** src/app/api/stripe/webhook/route.ts:35-63 — no validation that the completed session/subscription is actually for the premium product: `session.mode`, `session.payment_status`, and the subscription's price vs `process.env.STRIPE_PREMIUM_PRICE_ID` are never checked. Any current or future subscription on the same Stripe account (a different product, a $0 test price, a manually created subscription) sets `subscription_status='active'` and grants full premium.

**PAY-M7.** src/app/api/stripe/portal/route.ts:29-34 — unlike checkout/route.ts:41-56, the `stripe.billingPortal.sessions.create` call has no try/catch and no logging. The most common real-world failure here (Billing Portal configuration not saved in the Stripe dashboard for the given mode) throws, producing an unhandled 500 that the client's `await res.json()` in settings/page.tsx:239 cannot parse, so the paying customer sees a generic 'Something went wrong' with nothing logged for support.

**PAY-M8.** No automated coverage of the payment path at all: nothing under tests/ (auth-session, authenticated-features, core-loop-multi-user, fail-closed-screens, login-ui, persistence-boundary, prelogin) or playwright/ references stripe, premium, or entitlement. The entitlement function src/lib/premium.ts and the webhook state machine — the two pieces where a bug silently costs money or gives away product — have zero tests, including no negative test that a free user is rejected by /api/lists/ready-made/save or /api/import/library.

**PAY-M9.** src/lib/stripe.ts:9 — `new Stripe(process.env.STRIPE_SECRET_KEY!)` pins no `apiVersion`, while the webhook reads the newer per-item shape `subscription.items.data[0]?.current_period_end` (route.ts:54, 76).
