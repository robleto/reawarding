**No new criticals this round.** The only two critical/uncertain findings are the same deliberately-parked items from prior rounds: no Apple In-App Purchase path (PAY-1, large architectural work), and live-mode Stripe not yet configured (UNCERTAIN, a business/config decision, not a code bug).

**Severity mix (confirmed only, this round):** 2 critical, 7 high, 15 medium, 14 low.

Opus verifiers surfaced **56 further issues** during independent passes, not yet triaged — see the appendix.

**New high-severity findings this round** (not carried over, or promoted from a lower severity in a prior round):

1. **PAY-1** (critical). No Apple In-App Purchase path — iOS users hit a silent dead end with zero purchase or messaging
2. **PAY-5** (critical). Live-mode Stripe credentials appear never to have been configured — flow may only work in test mode
3. **CC-1** (high). ensureUserWatchlist doesn't recover from a concurrent unique-constraint race, leaving watchlist state silently null
4. **PERF-1** (high). usePublicProfile has no cache/dedup — every [username]/* page double- or triple-fetches the same profile payload
5. **PERF-2** (high). Film detail page runs 6 independent data fetches as a sequential waterfall
6. **PERF-3** (high). useMovieDataWithGuest fetches the entire movie catalog and up to 10,000 rankings rows on every Films/Rankings/Home mount — no server-side pagination
7. **AUTH-1** (high). OAuth signups never get a username-claim step, so social accounts permanently expose an email-derived string as their public /[username] URL
8. **LOOP-1** (high). Deleting a list wipes its items unconditionally before the list itself is confirmed deleted, with no error surfaced and no undo
9. **PAY-2** (high). Webhook has no refund handling, no invoice.payment_failed handling, no idempotency dedup, and freezes entitlement on any price change

### Code correctness & error handling

- src/lib/listEnrichment.ts:28-31 — PostgREST row-cap truncation silently corrupts movie_count and posters on the LIVE lists pages. The batched query `.from('movie_list_items').select('list_id, movie_id, ranking').in('list_id', listIds)` has no .limit() and no pagination, while supabase/config.toml:18 sets `max_rows = 1000`. Every row past 1000 is dropped, so `movie_count` at :67 (computed as `itemsByList.get(list.id)?.length`) is undercounted or 0 and `posterUrls` is empty for whichever lists fall past the cap. src/app/lists/home.tsx:143-157 calls this with up to PUBLIC_LISTS_LIMIT=50 public lists at once — exceeding 1000 total items across 50 lists is routine, not an edge case — and src/app/[username]/lists/page.tsx:86 has the same exposure. This is a regression introduced by the PERF-2 refactor referenced in the file's own header comment: the per-list pattern it replaced used `{ count: 'exact', head: true }`, which is cap-immune. Higher user impact than any of findings 2-4, and it sits in the exact code area the auditor was reviewing (it reviewed the dead useUserLists clone instead of the live shared helper).
- src/lib/listEnrichment.ts:28 and :54 — this is the live, reachable version of what the auditor filed against dead useUserLists. Both `const { data: itemRows } = await supabase...` and `const { data: movieRows } = await supabase...` discard `.error` entirely (not even destructured), and the function's return type has no error channel, so an RLS denial or transient PostgREST failure renders as 'every list has 0 films' on /lists and /[username]/lists with no indication anything failed. If the auditor's finding #3 is worth filing at all, it should have been filed here.
- src/app/lists/ready-made/[slug]/page.tsx:239-265 — the orphaned-list bug from finding #2, but in live code and worse. The movie_lists insert at :240-244 succeeds, then the item insert at :264 is `await supabase.from('movie_list_items').insert(items);` with the error not even destructured, and :273 redirects to `/lists/${listId}`. On an item-insert failure the user is redirected onto a brand-new permanently-empty list with no error surfaced at all — and because :242 sets `is_public: publishNow ? true : false`, the empty list can be published PUBLIC. Same shape recurs at :320-336 and :393-408 in this file.
- src/app/lists/ready-made/page.tsx:551-579 — same orphan pattern in the live `saveDirectorList` server action: movie_lists insert at :552-556, items insert at :575, and `if (itemsErr) redirect('/lists')` at :576-578 leaves the just-created empty list behind with no delete. - src/app/api/import/library/route.ts:430-432 — `continue` on a failed existence check causes a guaranteed unique-constraint failure that silently drops up to 500 good rows. When the `movie_list_items` existence probe for a chunk errors, the handler logs and `continue`s, so that chunk's already-present movie_ids are never added to `alreadyOnWatchlist` and therefore survive the `newWatchlistIds` filter at :439. The only trace is a console.error at :452; `watchlistCount` stays flat so the import reports success with a silently wrong number. Fix is an upsert with ignoreDuplicates or aborting rather than continuing.

### Performance & efficiency

# Detail: findings and verification notes by dimension

## Code correctness & error handling (CC)

The Reawarding codebase's API routes and hooks are unusually well-audited already — most files carry inline comments referencing prior audit passes (PAY-2, IMP-1/2/5, CC-2/6) that specifically fixed the exact classes of bugs this review was hunting for (race conditions, silent Supabase error swallowing, auth/entitlement checks, rollback-on-failure). The remaining gaps found are narrower: a real race condition in the shared watchlist-provisioning helper that can leave a signed-in user's watchlist stuck empty, an orphan-list bug on a premium list-save endpoint, and two hooks (useUserLists, useRecognitionFeed) that still silently drop Supabase query errors from secondary/enrichment fetches.

**Verifier's dimension assessment:** Two of four findings hold up; two are accurate code readings of unreachable code presented as user-facing defects.

The auditor's strongest work is finding #1 — I tried to break it (looked for a signup trigger that would pre-create the watchlist row, checked whether the unique-violation message would hit the jwt/session/auth suppression branch, checked whether the effect retries) and it survived every check. The two call sites really do live in the same app-wide component (src/app/providers.tsx:42 and :54), and the codebase's own import route at src/app/api/import/library/route.ts:261-267 documents the identical race as a known hazard. Only the "high" severity is inflated: the damage window is one render pass after signup and a reload self-heals.

The systemic weakness is that the auditor never checked reachability. Findings #3 and #4 are both dead code with literally zero call sites, and finding #2 targets an API route with no caller. For #4 the project's own CLAUDE.md names RecognitionFeed in an explicit list of unwired components and tells the reader to verify before assuming it renders — that instruction was available and ignored. Worse, in each case a live sibling with the same-or-worse bug went unexamined: src/lib/listEnrichment.ts is the reachable version of #3, and src/app/lists/ready-made/page.tsx plus [slug]/page.tsx hold four live copies of #2 (one of which, [slug]/page.tsx:264, does not even destructure the insert error and can leave a published-public empty list). Net effect is an audit weighted toward code that cannot fail while the equivalent live code went unreviewed.

Two of my misses outrank everything reported except #1. The max_rows=1000 truncation in src/lib/listEnrichment.ts:28 is a live data-correctness regression from the PERF-2 refactor that will already be firing on /lists for any account with 50 public lists in view, and the `continue` at src/app/api/import/library/route.ts:432 guarantees a unique-constraint rejection that silently discards up to 500 good watchlist rows while reporting success. Both sit squarely inside the file set the auditor opened.

Also note two of the confirmed findings' descriptions contain factual slips that would mislead whoever picks them up: #2 conflates the list's `name` with its `description` and misquotes the user-visible error, and #3 asserts the orphan surfaces via useUserLists, which never runs.

### CC-1 — ensureUserWatchlist doesn't recover from a concurrent unique-constraint race, leaving watchlist state silently null

**Severity:** high · **Effort:** small · **Verdict:** CONFIRMED

**Files:** `src/utils/watchlist.ts:8-47`, `src/hooks/useWatchlist.ts:44-52`, `src/utils/authMigration.ts:16-40`

`ensureUserWatchlist()` (src/utils/watchlist.ts) does SELECT-then-INSERT with no transaction/upsert, relying on the DB's partial unique index `uniq_user_watchlist` (supabase/migrations/20251114_add_list_type_to_movie_lists.sql) to prevent duplicate watchlists. But its catch block just logs and returns `null` on any error — it never re-queries to pick up the winning row after a unique-violation from a concurrent insert. Two call sites race on literally the same trigger: `useAuthMigration`'s effect (src/utils/authMigration.ts:37, fires on `user` becoming non-null) and `useWatchlist`'s effect (src/hooks/useWatchlist.ts:48, invoked from `WatchlistProvider` which is mounted app-wide and also keyed on `userId`) both call `ensureUserWatchlist(supabase, user.id)` independently as soon as a session appears — exactly the moment right after sign-in/sign-up when both mount/fire together. Whichever call loses the DB race gets a unique-constraint error, is caught, and returns `null`. In `useWatchlist.ts`, `listId` being null aborts the whole load effect (`if (cancelled || !listId) return;`), leaving `watchlistListId` and `watchlistMovieIds` stuck at their initial empty state for that component's lifetime — the user appears to have an empty watchlist and `toggle()`/`removeIfWatched()` return "You need to be signed in to use the watchlist" even though they are signed in and a watchlist row exists (created by the other, winning call).

**Verifier note:** Code reading is exact. src/utils/watchlist.ts:19-32 does SELECT-then-INSERT with no upsert/onConflict; the catch at :33-47 returns null and never re-SELECTs. supabase/migrations/20251114_add_list_type_to_movie_lists.sql:12-14 confirms the partial unique index `uniq_user_watchlist ON movie_lists(user_id) WHERE list_type='watchlist'`, so a losing concurrent insert raises 23505 — whose message contains neither 'jwt'/'session'/'auth', so it falls through to console.warn + return null. Both call sites are real and both mount app-wide in the SAME component: src/app/providers.tsx:54 calls useAuthMigration() (which hits ensureUserWatchlist at src/utils/authMigration.ts:37) and src/app/providers.tsx:42 mounts WatchlistProvider -> useWatchlist -> src/hooks/useWatchlist.ts:48. I checked for a DB-side signup trigger that would pre-create the row and make the race moot: none exists (no watchlist creation in any handle_new_user/on_auth_user_created migration), so a fresh user genuinely reaches the double-INSERT path. Downstream consequence verified: useWatchlist.ts:49 `if (cancelled || !listId) return;` bails before setting listIdRef/watchlistListId and before setting `error`, the effect deps are [userId, supabase] so it never retries, and toggleInner:75-77 then returns 'You need to be signed in to use the watchlist.' The only overstatement is severity: the window is one render pass right after signup and a page reload self-heals (the SELECT then finds the winning row). Supporting evidence the codebase already knows this hurts: src/app/api/import/library/route.ts:261-267 memoizes the promise specifically to avoid 'racing to create the list twice', and :418-419 has to log-and-skip when it resolves null.

**Task brief:** In src/utils/watchlist.ts's `ensureUserWatchlist`, when the insert fails with a unique-violation (Postgres code '23505', or more generally: on any insert error) re-run the SELECT for the existing watchlist row before giving up, and return that row's id instead of null. Add a regression test/manual repro: call `ensureUserWatchlist` twice concurrently for the same fresh user id and assert both calls resolve to the same non-null list id.

## Performance & efficiency (PERF)

The app's biggest performance liabilities are data-fetching patterns, not rendering: several client hooks fetch entire tables (or duplicate the same profile payload) instead of paginating or sharing a cache, and one key server page (the film detail page) chains six independent Supabase/API calls sequentially instead of running them in parallel. There is also a concrete unnecessary-re-render bug (an unmemoized MovieCard subscribed to a broad watchlist context) and several movie-poster surfaces that bypass the app's own next/image-based MovieCard pattern with raw img tags.

**Verifier's dimension assessment:** Unusually high-quality audit for this dimension: all seven findings are real code-level observations, none were misreads, and the two big ones (the 3,000-row unpaginated catalog fetch and the film-detail waterfall) are the correct top-two picks. I verified the data-side assumptions against the live DB with the repo's read-only script (4,376 movies, avg 270-char overview, 1,079 posters still on TMDB /t/p/original/, 11 users, 1,277 rankings), and they hold or understate the problem. Weaknesses are in supporting reasoning rather than in the findings: the Cache-Control header in finding 1 is a browser directive, not CDN-only; finding 4's proposed React.memo comparator would not fix a context-driven re-render; finding 7 attributes framer-motion to page.tsx when it actually ships via AppShell -> BackToTopButton, and wrongly says client components are not server-rendered. The most notable gap is that the auditor never checked memoization of the derived data it correctly identified as huge — films/page.tsx and rankings/page.tsx contain zero useMemo and re-filter/sort/group the entire catalog on every render, which is a smaller, cheaper fix than the proposed server-side pagination and probably the single best performance-per-effort item in the codebase. Also missed: the N+1 in useUserLists, the one-size-fits-all heavy /api/users payload feeding profile tabs that only need a name, and the unscoped all-users watchlist-id query on the film detail page.

### PERF-1 — usePublicProfile has no cache/dedup — every [username]/* page double- or triple-fetches the same profile payload

### IMP-2 — CSV parser splits the file into lines before quote-aware parsing, silently misaligning rows with embedded newlines
